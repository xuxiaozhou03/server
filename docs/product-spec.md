# Product Studio 产品与技术说明

> 状态：第一版产品范围已确认
> 更新日期：2026-11-12
> 文档定位：本文件是当前产品唯一有效说明，同时承载产品边界、研发链路、技术资产约束和第一版验收标准
> 适用方式：产品、设计、开发、测试和运维均以本文件为共同上下文；不再维护拆分副本

---

## 1. 产品定义

**Product Studio 是一个本地产品展示和项目管理控制面。**

它不负责执行研发任务。需求分析、原型制作、代码开发、测试执行和运维操作，由不同角色使用本地 Codex 在同一个产品仓库中完成。Studio 负责：

- 以需求为主线展示产品、原型、设计语言、数据库、API、代码证据和交付状态。
- 管理需求、任务、负责人、协作人、依赖、状态流转、Bug 和验收。
- 为产品、技术负责人、后端、前端、测试和运维提供可直接交给本地 Codex 的完整上下文。
- 将 PR、迁移、测试报告、Swagger 变更和验收结论关联回需求。
- 根据任务和证据计算需求进度，执行完成门禁。

一句话边界：

> **Studio 负责展示、组织和项目管理；本地 Codex 和人工负责真正的工作。**

Studio 不是在线 SaaS、多人实时协作平台、代码执行平台或自动化研发代理。

第一版运行方式：

- 一个仓库只承载一个产品。
- 一个 Studio 本地实例，一个活动操作人。
- 角色是工作职责和上下文身份，不是账号、登录状态或权限。
- 同一操作人可以切换不同角色使用本地 Codex，但角色动作和证据必须分别留痕。
- 产品事实和项目管理记录全部使用仓库纯文件，不使用 Studio SQLite。

核心链路：

```text
产品提出需求
→ 产品使用本地 Codex 生成需求文档、原型和 Tour
→ 技术负责人人工评审
→ 在 Studio 拆分任务并分配角色
→ 各角色使用本地 Codex 执行
→ 证据回填 Studio
→ Studio 管理状态和完成门禁
→ 人工验收通过
```

## 2. 要解决的问题

1. 需求、页面、数据、接口、代码和测试缺少稳定关联。
2. 需求文档、原型和正式代码分散，开发前需要重复解释和转换。
3. 数据库设计、迁移 SQL、OpenAPI 和正式实现容易漂移。
4. 设计语言停留在截图和说明，缺少真实组件、预览和测试。
5. 单人本地开发缺少角色化上下文，前后端、测试和运维容易漏项。
6. 页面完成后无法说明它属于哪个需求、改了什么、还缺什么。
7. 代码已经更新，产品文档、测试证据和验收结论却停留在旧状态。

Product Studio 要解决的问题不是“展示更多页面”，而是：

> **让一个需求从提出到验收始终可解释、可追踪、可验证，并能为本地 Codex 提供稳定上下文。**

## 3. 第一版边界

### 3.1 单产品仓库

一个仓库只承载一个产品，目标采用 pnpm workspace。仓库同时包含：

- 产品定义、需求、页面和 Tour
- 设计语言、真实组件、组件预览和组件测试
- 数据库设计、迁移记录和迁移 SQL
- OpenAPI 契约和 Swagger 展示
- 独立原生 HTML 原型
- 正式前端、正式后端
- Product Studio
- 测试、Bug、交付、发布和验收记录

### 3.2 单一事实源

- 产品和交付事实以仓库文件为准。
- Studio 不维护第二份产品正文，不使用独立项目管理数据库。
- Studio 可以在内存中建立索引，进程重启后从文件重新加载。
- 原型、正式代码和产品文档随同一次变更提交。
- 文件与实现不一致时应校验失败，而不是依赖人工判断哪一份最新。

### 3.3 本地单人工作台

- 同一工作区只允许一个 Studio 写实例。
- 同一时刻只有一个活动操作人。
- 成员目录用于负责人、角色、筛选和计划，不代表登录账号或在线状态。
- 不提供账号、权限、SSO、远程共享和实时多人编辑。
- 跨人员协作通过 Git、分支和代码审阅完成。
- Studio 只记录实际本地操作者，不伪造角色登录行为。

### 3.4 桌面端优先

第一版只保证电脑端展示，不处理手机和平板适配。

## 4. 产品原则

1. **需求为根**：首页和项目管理按需求组织，不首先展示全量页面或孤立任务。
2. **展示与管理分离**：Studio 管理事实和状态，不执行需求、代码、测试或部署。
3. **本地 Codex 执行**：角色通过本地 Codex 修改仓库，Studio 接收文件、PR、报告和证据。
4. **最新代码即产品文档**：产品说明与正式代码同仓、同变更、可审阅。
5. **设计语言可运行**：设计语言由规则、token、真实组件、预览服务和测试共同构成。
6. **原型独立**：原型用于沟通、Tour 和交互验证，不参与正式构建、正式测试和发布。
7. **契约驱动**：数据库设计和 OpenAPI 是正式资产，页面必须声明关联。
8. **人工确认**：规则和 AI 可以生成草稿，评审、任务确认和最终验收必须由人完成。
9. **完整闭环**：代码合并不等于需求完成，只有验收通过才算完成。
10. **信息可追溯**：需求、页面、任务、PR、迁移、测试、Bug 和证据可以双向定位。

## 5. 角色与工作方式

| 角色 | 主要工作 | 使用方式 | 关键产物 |
| --- | --- | --- | --- |
| 产品 | 提出需求，明确目标、范围、规则和验收标准 | 人工 + 本地 Codex | 需求文档、原型、Tour、验收标准 |
| 设计师 | 定义视觉意图、组件选择、样式和交互约束 | 人工 + 本地 Codex + 设计预览 | 设计语言、组件、示例、测试 |
| 技术负责人 | 评审需求与技术闭环，拆分任务并分配角色 | 人工评审 + Studio 项目管理 | 评审结论、任务树、依赖和负责人 |
| 后端 | 调整数据库、迁移、接口、实现和自测 | 本地 Codex | Schema、迁移 SQL、OpenAPI、代码、PR、自测报告 |
| 前端 | 生成接口文件、实现页面、联调 | 本地 Codex | API 类型或客户端、页面代码、PR、联调记录 |
| 测试 | 生成并执行验收、契约和集成测试，提出 Bug | 本地 Codex | 测试用例、报告、Bug、回归结论 |
| 运维 | 部署、迁移、监控、回滚和发布验证 | 本地 Codex | 运维记录、发布证据、回滚结果 |
| 验收人 | 确认业务目标是否真正达成 | 人工 | 验收结论和签核 |

角色身份不改变 Studio 的单操作人事实。Studio 记录“以什么职责完成了什么动作”，而不是模拟多个在线用户。

## 6. 标准研发流程

### 6.1 需求提出与生成

1. 产品人工提出需求，在 Studio 登记需求元信息并关联目标页面。
2. 产品使用本地 Codex 读取设计语言、现有需求和产品资产。
3. Codex 生成或更新需求文档、独立 HTML 原型、Tour 演示路径和验收标准。
4. 需求正文、原型和关联资产写回仓库，并在 Studio 中展示。
5. 需求进入待评审状态。

需求文档至少包含：

```text
身份：ID、标题、负责人、协作人、优先级、计划日期
意图：背景、问题、目标、用户、成功指标
范围：做什么、不做什么、受影响页面
规则：业务流程、状态、异常、边界和权限语义
设计：设计语言、组件、交互约束和原型入口
Tour：演示起点、跨页步骤、目标 DOM 和预期结果
技术：数据表、迁移、operationId、兼容性影响
验收：可观察的验收标准、边界和所需证据
依赖：前置需求、外部条件和待确认项
```

### 6.2 技术负责人评审

技术负责人必须人工检查：

- 需求目标、范围和非目标是否清晰。
- 验收标准是否可测试或可人工观察。
- 页面、数据、接口、组件和测试是否形成闭环。
- 数据库迁移、接口兼容性、风险和回滚是否明确。
- 是否存在阻塞性待确认项。

评审通过后，Studio 记录评审人、时间、结论和评审意见。未通过时需求退回产品修改，不得进入开发。

### 6.3 任务拆分与分配

技术负责人采用：

> **规则生成 + AI 补全 + 人工确认**

规则负责稳定的拆分骨架，本地 Codex 补全任务描述、影响文件、风险和验证命令，技术负责人人工确认范围、负责人和依赖。

最小任务类型：

| 类型 | 何时需要 | 完成证据 |
| --- | --- | --- |
| `requirement` | 所有需求 | 需求正文、范围和确认记录 |
| `prototype` | 需要交互验证或 Tour 时 | 原型页面、Tour 脚本和确认记录 |
| `design` | 设计语言、组件或预览变化 | 组件源码、注册表、预览、测试和确认 |
| `data` | 表、字段、关系或迁移变化 | Schema、迁移 SQL 和校验结果 |
| `contract` | OpenAPI 或共享类型变化 | 契约校验和受影响页面清单 |
| `backend` | 后端逻辑或接口变化 | 后端 PR、自测、Swagger 和迁移记录 |
| `frontend` | 正式前端变化 | 前端 PR、接口文件和联调记录 |
| `test` | 所有需求 | 测试用例、命令、报告和覆盖结论 |
| `ops` | 部署、配置、迁移、监控或回滚 | 执行结果、监控和回滚证据 |
| `bug` | 测试或验收发现问题 | 复现、修复、回归和关闭证据 |
| `docs` | 产品、接口或运维说明变化 | 文档变更和评审记录 |

拆分规则：

- 每个任务只有一个明确交付物。
- 数据先于依赖它的接口，契约先于前后端实现。
- 测试任务与开发任务同时创建。
- 每个任务必须有负责人、依赖、上下文、完成证据和验收标准。
- 依赖必须形成无环图。
- 不涉及的交付项必须标记 `not_applicable` 并说明原因。

### 6.4 角色执行与证据回填

后端角色使用本地 Codex：

```text
读取需求和任务上下文
→ 修改数据库设计与 Prisma Schema
→ 生成并检查迁移 SQL
→ 更新 OpenAPI 和 Swagger 文档
→ 实现 Hono.js 接口和业务逻辑
→ 执行自测、契约测试和迁移验证
→ 提交 PR 和证据
```

前端角色使用本地 Codex：

```text
读取页面、设计语言和 OpenAPI
→ 生成或更新接口类型/客户端
→ 使用 shadcn/ui 和 @product/ui 实现页面
→ 完成状态、错误、空态和交互
→ 启动前端与后端联调
→ 提交 PR、页面检查和联调证据
```

测试角色使用本地 Codex：

```text
读取需求、验收标准和测试上下文
→ 生成验收用例、API 契约测试和集成测试
→ 准备测试数据和环境
→ 执行测试并保存报告
→ 在 Studio 登记失败项和 Bug
→ 回归修复并提交结论
```

运维角色使用本地 Codex：

```text
读取发布与迁移要求
→ 执行部署、配置和迁移
→ 检查健康状态、日志、监控和告警
→ 验证回滚路径
→ 回填发布和运维证据
```

所有执行结果由角色写回仓库或外部工具，再由 Studio 关联到需求、任务和交付证据。Studio 不直接运行这些命令。

## 7. Studio 的能力与职责

| 能力 | Studio 负责 | Studio 不负责 |
| --- | --- | --- |
| 需求展示 | 登记元信息、关联资产、展示正文、范围、原型和验收标准 | 代替产品分析需求或生成正文 |
| 上下文交付 | 聚合需求、设计、数据、接口、代码入口、命令和风险 | 执行开发、测试或部署 |
| 页面与 Tour | 左侧展示真实原型，右侧展示页面需求和 Tour 步骤 | 把原型作为正式前端运行 |
| 设计语言 | 展示规则、token、真实组件、变体、示例和测试结果 | 维护第二套静态组件 |
| 数据库 | 展示表、字段、关系、索引、迁移记录、SQL 和关联需求 | 启动或连接本地业务数据库 |
| API | 展示和维护 `openapi.json`，渲染 Swagger 风格文档 | 代替后端实现接口 |
| 项目管理 | 需求、任务、负责人、依赖、状态、Bug、活动记录和完成门禁 | 绕过证据直接完成需求 |
| 证据 | 关联 PR、测试报告、迁移、发布和验收结论 | 自动伪造或推断未验证的结果 |
| 持久化 | 通过受控写操作维护仓库文件 | 维护独立项目数据库或影子状态 |

### 7.1 首页与需求中心

首页以需求为维度展示，不首先展示全量页面。

每个需求至少显示：

- 标题、负责人、优先级和期限
- 当前阶段与完成比例
- 关联页面和原型
- 技术负责人评审状态
- 数据库、API、前端、后端、测试、Bug 和运维摘要
- 当前阻塞项和下一步动作

需求详情使用 `/requirements/<requirement-id>`，包含完整上下文、任务树、变更记录、证据和验收门禁。

### 7.2 页面工作台与 Tour

每个原型页面使用独立 HTML，不通过一个 HTML 内部隐藏切换模拟多个页面。

页面工作台采用：

- 左侧：真实原型画布
- 右侧：本页需求、需求改动、验收点、数据表、API、组件、测试、变更记录和技术闭环

页面路由使用 `/p/<page-id>`，不包含产品目录前缀：

```text
/p/dashboard
/p/orders
/p/customers
```

Tour 是需求演示和验收的一部分，必须支持：

- 从指定页面和步骤开始。
- 跨页面切换。
- 绑定真实 DOM 选择器。
- 高亮、引导文案和预期结果。
- 关联需求 ID 和验收点。
- 在 Studio 中直接播放。

Tour 仍然作为普通需求走完整流程，但需求上下文必须保留演示脚本和预期路径。

### 7.3 设计语言与组件预览

第一版正式前端采用：

```text
React + Vite + shadcn/ui + Tailwind CSS
```

设计语言不是静态色板，也不是另一套仅供展示的 HTML。它由以下资产组成：

| 资产 | 职责 |
| --- | --- |
| `product/design/design-language.md` | 设计意图、布局、排版、交互、组件选择和正反例，供人与 Codex 直接读取 |
| `product/design/tokens.json` | 颜色、字体、字号、间距、圆角、阴影和动效的机器可读源 |
| `product/design/components.json` | 组件 ID、分类、入口、变体、尺寸、状态和稳定级别 |
| `packages/ui` | shadcn/ui 基础组件和二次封装业务组件的真实实现 |
| `packages/ui/**/*.test.tsx` | 组件测试代码，供 Codex 理解和验证行为 |
| `apps/design-preview` | 直接导入真实组件的预览、规范和测试展示服务 |

`packages/ui` 至少分为：

```text
packages/ui/
├── src/
│   ├── components/ui/       # shadcn/ui 基础组件
│   ├── components/product/  # 二次封装业务组件
│   ├── lib/cn.ts            # className 合并
│   └── index.ts             # 唯一公开导出入口
└── package.json
```

设计预览服务必须支持：

- 真实组件导入，不允许复制 JSX 或维护静态副本。
- 基础组件和业务组件列表。
- 变体、尺寸、状态、Props、事件和可访问性说明。
- 使用示例、import 示例、源码路径和组件 ID。
- 正例、反例、禁止用法和 Tailwind 约束。
- 组件测试代码、测试命令和最近结果。
- 主题、参数和交互状态切换；参数只用于预览，不回写源码。
- 生成可交给本地 Codex 的调整上下文。

设计师通过本地 Codex 新增或修改设计语言，在 `/p/design` 的预览服务中确认真实效果。首版不建设可视化设计编辑器。

### 7.4 数据库设计

Studio 展示数据库设计，不要求第一版在本地启动业务数据库。

数据库资产包括：

```text
product/database/schema.json                         # 数据库结构设计
apps/api/prisma/schema.prisma                        # 正式后端实现表示
apps/api/prisma/migrations/<timestamp>_<name>/       # 迁移记录
apps/api/prisma/migrations/<timestamp>_<name>/migration.sql
```

Studio 至少展示：

- 表、字段、类型、主键、外键、索引和约束。
- 表关系和 ER 图。
- 字段说明和关联页面。
- 迁移版本、名称、时间和影响表。
- 每个迁移的完整 SQL。
- 迁移关联的需求、任务、PR 和测试。
- 设计结构与 Prisma Schema 的一致性差异。

数据库设计与 Prisma Schema 不得各维护一份无约束的手工副本；应通过生成或校验保持一致。

### 7.5 API 设计与 Swagger

`product/api/openapi.json` 是唯一 API 契约源。

Studio 提供：

- 结构化的 API 设计查看和必要编辑。
- 操作、请求、响应、错误和鉴权约束。
- Schema、示例、`operationId` 和 Tag。
- Swagger 风格只读文档。
- 页面、前端任务和接口的双向引用。
- 未使用、未实现和断链接口检查。
- OpenAPI 保存前校验。

后端使用本地 Codex 实现接口并更新 OpenAPI。Studio 只展示和维护契约，不代替后端编写业务逻辑。

### 7.6 项目管理与任务流转

第一版提供本地项目管理：

- 需求列表和需求任务树
- 任务看板和列表
- 任务负责人、协作人、优先级和期限
- 任务依赖和阻塞关系
- 成员待办与人员分配视图
- 需求、任务、Bug、测试和证据详情
- 指派、状态、评论和证据变更活动记录
- PR、测试和验收结果关联

任务状态：

```text
draft → unassigned → ready → in_progress → in_review → done
                                  └──────→ blocked
done → reopened → in_progress
```

任务状态流转都在 Studio 项目管理面执行。本地 Codex 可以产生实现、测试和证据，但不能绕过 Studio 直接修改项目管理状态。

需求状态：

```text
draft → planned → in_progress → acceptance → done
                    ↘ blocked
cancelled
```

需求状态由任务、PR、测试、Bug、运维和验收结果聚合，不能手工选择 `done` 绕过门禁。

### 7.7 Bug 与回归

```text
open → triaged → fixing → fixed → in_regression → closed
                     └──────────→ rejected
closed / rejected → reopened
```

- 测试或验收角色使用本地 Codex 产生复现和 Bug 证据。
- 开发角色使用本地 Codex 修复。
- Studio 记录 Bug、关联证据并管理状态流转。
- `fixed` 只表示修复已提交，不代表 Bug 关闭。
- 回归通过后才能关闭；未关闭的有效 Bug 阻断需求完成。

## 8. 需求上下文

技术负责人评审通过后，Studio 必须为每个角色提供可直接交给本地 Codex 的上下文。

### 8.1 产品上下文

- 需求目标、背景、用户和成功指标
- 范围和非目标
- 业务规则、异常和边界
- 需求文档路径
- 原型入口和 Tour 脚本
- 设计语言、组件约束和验收标准

### 8.2 技术负责人上下文

- 受影响页面、数据表、迁移和接口
- 组件和代码入口
- 跨端依赖、兼容性和风险
- 评审项、阻塞项和待确认问题
- 任务拆分建议、测试范围和完成门禁

### 8.3 后端上下文

- 需求与验收标准
- `schema.json`、Prisma Schema 和已有迁移
- 需要新增的迁移和 SQL 检查要求
- OpenAPI 操作、请求、响应和错误
- 后端代码入口、共享类型和依赖
- 自测、契约测试、迁移验证命令
- PR 和 Swagger 证据要求

### 8.4 前端上下文

- 页面、路由、状态和交互
- 原型、Tour 和本页需求改动
- 设计语言、组件 ID、变体和预览入口
- OpenAPI 生成的接口类型或客户端
- 前后端联调环境和测试数据
- 页面检查、E2E 和验收标准

### 8.5 测试上下文

- 业务规则、验收标准和边界
- 已有测试和覆盖缺口
- 测试类型、数据、环境和账号语义
- API 契约测试、集成测试和 E2E 要求
- Bug 提交、修复和回归流程
- 必需报告、命令和证据

### 8.6 运维上下文

- 部署、配置和迁移要求
- 健康状况、日志、监控和告警
- 回滚条件和操作步骤
- 发布后冒烟验证
- 责任人和证据要求

所有上下文都是同一需求事实的裁剪视图，不是多份独立正文。需求变化后，受影响上下文和任务必须标记待复核。

## 11. 状态、证据与完成门禁

### 11.1 两级门禁

| 门禁 | 范围 | 通过含义 |
| --- | --- | --- |
| 可合并 | 单个 PR | 变更可以安全进入主干 |
| 需求完成 | 整个需求 | 满足业务目标并完成验收 |

单个 PR 合并前至少满足：

- 关联需求、任务和受影响页面。
- Schema、OpenAPI 和组件注册表校验通过。
- 页面、数据和接口引用完整。
- 对应自动化测试通过。
- 必要代码审阅完成。
- 迁移、兼容性和回滚影响已说明。

### 11.2 需求完成条件

需求完成必须同时满足：

- 需求文档已确认并与最终实现一致。
- 技术负责人评审已通过。
- 原型和 Tour 已确认，或明确标记不适用。
- 设计语言、数据库、迁移和 OpenAPI 已完成并校验通过。
- 前端任务完成，前端 PR 已合并。
- 后端任务完成，后端 PR 已合并。
- 运维任务完成，并记录验证证据。
- 验收用例、API 契约测试和集成测试通过。
- 关键 E2E 通过。
- 有效 Bug 全部关闭并完成回归。
- 人工验收签核通过。

以下情况不能完成需求：

- 任一必需交付项未开始、进行中、阻塞、失败或过期。
- PR 未合并。
- 迁移只改了 Prisma Schema，没有迁移 SQL 或验证记录。
- Swagger 文档与 OpenAPI 或后端实现不一致。
- Bug 只标记修复，尚未回归。
- 缺少验收证据或验收人签核。
- 手工修改状态绕过门禁。

需求完成以**验收通过**为准，不以代码合并或发布为准。

## 12. 第一版范围

第一版必须提供：

1. 单产品 pnpm workspace 和 Studio 桌面端导航。
2. 以需求为维度的首页、需求详情和角色上下文。
3. 独立 HTML 页面原型、左侧画布、右侧说明和 Tour。
4. 数据库结构、迁移记录和迁移 SQL 展示。
5. OpenAPI 设计、Swagger 文档和页面/任务引用。
6. shadcn/ui + Tailwind 的真实组件库、测试和设计预览服务。
7. 本地项目管理和任务看板，包括负责人、角色、依赖和受控流转。
8. 后端、前端、测试和运维任务上下文。
9. 验收用例、API 契约测试、集成测试、E2E 和 Bug 回归。
10. PR、迁移、测试、运维和人工验收组成的完成门禁。
11. 纯文件持久化和进程内索引，不引入 Studio SQLite。

第一版不做：

- 账号、登录、权限、组织架构、SSO 和审批系统。
- 在线团队服务、远程共享和实时多人协作。
- GitHub Issues、Linear、Jira 等外部任务系统。
- Studio 代替角色执行代码、测试或部署。
- 可视化拖拽式需求或设计编辑器。
- 多产品、多项目层级。
- 移动端和平板适配。
- 原型参与正式构建、正式测试或发布。
- Studio 独立数据库或持久化查询缓存。
- 用截图或静态样板冒充真实设计组件。

## 15. 第一版验收

第一版完成时，应能完整演示：

1. 产品提出需求，并在 Studio 登记和关联多个页面。
2. 产品使用本地 Codex 生成需求文档、独立 HTML 原型和 Tour。
3. 技术负责人查看技术闭环并人工评审通过。
4. 技术负责人完成规则生成、AI 补全和人工确认的任务拆分。
5. 任务分配到后端、前端和测试角色，并带有完整上下文。
6. 后端角色通过本地 Codex 修改数据库、生成迁移 SQL、更新 OpenAPI、实现接口并自测。
7. 前端角色通过本地 Codex 生成接口文件、实现页面并完成联调。
8. 测试角色通过本地 Codex 生成验收用例、API 契约测试和集成测试，并提交 Bug。
9. 在 Studio 中查看 Swagger、数据库迁移和迁移 SQL。
10. 在 `/p/design` 查真实组件、变体、规范、示例和测试代码。
11. 在 Studio 完成任务开始、阻塞、评审、完成、退回和重开。
12. 查看 PR、迁移、测试、Bug、运维和验收证据自动聚合成需求门禁。
13. 未关闭 Bug、未合并 PR、缺失迁移或测试失败会阻断需求完成。
14. 人工验收通过后需求才变为完成。
15. 重启 Studio 后所有事实仍能从仓库文件恢复。
16. 不依赖 Studio SQLite、外部任务系统或多人账号系统。

## 16. 结论

第一版不追求“大而全的研发平台”，而追求一条真实可运行的本地闭环：

> **产品用本地 Codex 产出需求、原型和演示；技术负责人评审并拆分；各角色用本地 Codex 完成设计、开发、测试和运维；Studio 展示资产、分发上下文、管理任务并验证完成门禁；只有人工验收通过，需求才算完成。**
